### 1. Архитектура

Монолитный набор сервисов на одном VPS, оркестрируемый **Docker Compose**. Единый источник правды — одна БД. Бизнес-логика вынесена в общий пакет `core`, который импортируют и бот, и веб (чтобы не дублировать).

```
                 ┌───────────────────────────────────────────┐
   Telegram ───▶ │  bot (aiogram)                            │
                 │   ingest → STT/OCR → LLM → CRUD (core)     │
                 │   команды/сценарии + планировщик отчётов   │
                 └───────────────┬───────────────────────────┘
                                 │           ▲
                                 ▼           │ общая БД
   Браузер ─HTTPS─▶ nginx ─▶ web (FastAPI)   │
                 │   REST API + статика (React SPA)           │
                 └───────────────┬───────────────────────────┘
                                 ▼
                          ┌─────────────┐   нет доступа на запись
                          │  SQLite БД  │◀────────────────┐
                          └──────┬──────┘                 │
                                 │ копия файла            │
                          ┌──────▼────────────────────────┴──┐
                          │ backup (cron, отдельный OS-user)  │
                          │ суточные срезы; ИИ не может менять │
                          └───────────────────────────────────┘

   Внешние ИИ-сервисы (через абстракции, конфигурируемо):
     LLM: OpenAI-совместимый endpoint (YandexGPT / DeepSeek / Ollama)
     STT: Yandex SpeechKit / Whisper
     OCR: Yandex Vision / Tesseract
```

**Компоненты:**
- **core** — модели данных, доступ к БД, абстракции LLM/STT/OCR, бизнес-логика сценариев (план дня, аналитика, парсинг, связывание). Общая библиотека.
- **bot** — приём сообщений TG, конвейер ingest, сценарии, inline-подтверждения, планировщик (APScheduler).
- **web** — REST API (FastAPI) + отдача React SPA. Использует `core`.
- **db** — SQLite (файл на volume).
- **backup** — изолированное резервное копирование.
- **nginx** — TLS, статика, прокси `/api` → web.

### 3. Модель данных

Единая таблица **`items`** с дискриминатором `type` — из-за сильной полиморфности (теги, вложения, комментарии, связи, членство в проекте применимы к любому типу). Плюс справочные и связующие таблицы. Псевдо-DDL (SQLite):

```sql
-- Основная сущность (задача/идея/заметка/проект)
items (
  id            INTEGER PRIMARY KEY,
  type          TEXT NOT NULL CHECK (type IN ('task','idea','note','project')),
  title         TEXT,                 -- суть/наименование (для note может генерироваться ИИ)
  description   TEXT,                 -- описание (для note — тело)
  status        TEXT,                 -- task: active|done|cancelled|delegated
                                      -- idea: active|archived
                                      -- project: active|done|cancelled
                                      -- note: NULL
  priority      TEXT,                 -- только task: asap|high|medium|low
  deadline      DATETIME,             -- task, project (опц.)
  delegated_to  TEXT,                 -- task при status='delegated' (опц.)
  note_date     DATE,                 -- note: структурированная дата (напр. ДР)
  note_recurrence TEXT,               -- note: none|yearly|monthly (опц.)
  project_id    INTEGER REFERENCES items(id),  -- членство в проекте (task/idea/note)
  source_text   TEXT,                 -- сырой результат STT/OCR (хранится по умолчанию, FR-3)
  created_at    DATETIME NOT NULL,
  updated_at    DATETIME NOT NULL,
  deleted_at    DATETIME              -- soft-delete (NFR-5, обратимость)
);

tags (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,
  is_preset  BOOLEAN NOT NULL DEFAULT 0   -- преднастроенные: работа, дом, ремонт, идеи
);

item_tags (
  item_id  INTEGER NOT NULL REFERENCES items(id),
  tag_id   INTEGER NOT NULL REFERENCES tags(id),
  PRIMARY KEY (item_id, tag_id)
);

comments (                              -- комментарий = хронология (append-only)
  id         INTEGER PRIMARY KEY,
  item_id    INTEGER NOT NULL REFERENCES items(id),
  text       TEXT NOT NULL,
  created_at DATETIME NOT NULL
);

attachments (                           -- явно сохранённые/прикреплённые медиа (FR-3, FR-8)
  id             INTEGER PRIMARY KEY,
  item_id        INTEGER NOT NULL REFERENCES items(id),
  kind           TEXT NOT NULL CHECK (kind IN ('image','audio')),
  file_path      TEXT,                  -- заполнено ТОЛЬКО если оригинал сохранён
  extracted_text TEXT,                  -- результат STT/OCR
  created_at     DATETIME NOT NULL
);

links (                                 -- двунаправленные связи между любыми items
  id            INTEGER PRIMARY KEY,
  item_low_id   INTEGER NOT NULL REFERENCES items(id),   -- канонический порядок low<high
  item_high_id  INTEGER NOT NULL REFERENCES items(id),
  UNIQUE (item_low_id, item_high_id)
);

settings (                              -- одна строка (id=1), редактируется в web и TG
  id                     INTEGER PRIMARY KEY CHECK (id = 1),
  timezone               TEXT NOT NULL DEFAULT 'Asia/Barnaul',   -- UTC+7
  morning_report_enabled BOOLEAN NOT NULL DEFAULT 0,
  morning_report_time    TEXT NOT NULL DEFAULT '08:30',          -- HH:MM
  notification_mode      TEXT NOT NULL DEFAULT 'on_request'
);

users (                                 -- один пользователь (веб-логин)
  id            INTEGER PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL
);

audit_log (                             -- лог изменений (NFR-5); ключ для действий ИИ
  id         INTEGER PRIMARY KEY,
  actor      TEXT NOT NULL,             -- 'user' | 'ai'
  action     TEXT NOT NULL,             -- create|update|status_change|delete|link|...
  item_id    INTEGER,
  before     TEXT,                      -- JSON снимок до
  after      TEXT,                      -- JSON снимок после
  created_at DATETIME NOT NULL
);
```

**Индексы:** `items(type)`, `items(status)`, `items(deadline)`, `items(project_id)`, `items(deleted_at)`, `items(note_date)`, `item_tags(tag_id)`, `links(item_low_id)`, `links(item_high_id)`, `comments(item_id)`.

**Замечания по модели:**
- Членство в проекте — через `project_id` (одна запись — один проект; вложенность проектов не предусмотрена).
- «Связи» (`links`) и «членство» (`project_id`) — разные механизмы: связь = ассоциация равных, членство = вхождение в проект.
- Soft-delete (`deleted_at`): ИИ помечает удаление, но не стирает данные физически (обратимость).

### 4. Компоненты и логика

#### 4.1 Конвейер приёма (ingest) — FR-1…FR-8
1. Приём сообщения из TG: определить тип контента (text / voice / photo).
2. **voice** → `STTClient.transcribe()` → текст; **photo** → `OCRClient.extract()` → текст; **text** → как есть.
3. Полученный текст сохраняется как `source_text` (по умолчанию оригинал медиа **не** сохраняется — FR-3).
4. `LLMClient` определяет **намерение** (FR-4): `new_item` / `query` / `edit`.
5. Если `new_item` — `LLMClient` делает **структурированное извлечение** (JSON по схеме): тип(ы) сущности, суть, описание, сферы, проект (если явно), дедлайн, приоритет; для заметок — `note_date`/`recurrence` (напр. «ДР 21 июля» → дата + yearly). Один ввод может дать несколько записей (FR-6).
6. Запись(и) создаются в БД; бот отвечает **карточкой-подтверждением** (FR-7) с inline-кнопками «Изменить / Отменить». Повторно не переспрашивает.
7. Сохранение оригинала медиа — отдельным действием по явному запросу (кнопка/команда) → создаётся `attachments` с `file_path`.

**Структурированный вывод LLM (пример схемы ответа):**
```json
{
  "intent": "new_item",
  "items": [
    {"type":"task","title":"...","description":null,"tags":["работа"],
     "project":null,"deadline":"2026-07-22","priority":"high",
     "note_date":null,"note_recurrence":null}
  ]
}
```
Модель обязана возвращать **только валидный JSON** (без обрамления). Парсинг — со strict-валидацией и фолбэком (переспросить/создать как заметку при ошибке).

#### 4.2 Маршрутизация намерений и команды — FR-4, FR-23
- Основной путь — определение намерения через LLM.
- Надёжный резерв — слэш-команды: `/plan`, `/report`, `/find <текст>`, `/done <id|описание>`, `/help`, `/settings`. Команды исполняются детерминированно, минуя LLM-классификацию.
- Лёгкие правки из TG (FR-9): сменить дедлайн/сферу/проект, добавить комментарий, сменить статус.

#### 4.3 Сценарии-запросы

**«План на день» (FR-17) — детерминированная выборка + оформление LLM:**
1. `tasks`: `status='active' AND date(deadline)=today` → сортировка по приоритету (`asap>high>medium>low`).
2. `tasks`: `status='active' AND deadline IS NULL AND priority='asap'`.
3. `notes`: `note_date` совпадает с сегодня (с учётом `recurrence`, напр. yearly → сравнение по дню-месяцу) → блок «дополнительно» (напр. ДР).
4. Для каждой задачи из п.1 — подтянуть связанные (`links`) идеи/заметки → показать как связанный контекст.
5. Собранная структура передаётся LLM **только для форматирования** ответа (не для поиска) — экономия токенов и отсутствие галлюцинаций.

**«Аналитика дня» (FR-18):** агрегаты по БД (число завершённых задач за день, число идей, разбивка по сферам/проектам) → LLM формирует краткий связный вывод.

**Поиск/выборки (FR-22):** список по сфере / проекту / статусу; текстовый поиск по `title`/`description`/`comments` (SQL LIKE / FTS5 при необходимости).

**Смена статуса (FR-20, FR-21):** по явному сообщению пользователя. Бот **не** инициирует запрос статуса сам.

#### 4.4 Гибридное связывание — FR-19
- **Детерминированный костяк:** явные `links`, `project_id`, `note_date`.
- **ИИ-подсказки:** при создании записи — ограниченный поиск кандидатов на связь (по пересечению ключевых слов/тегов среди активных записей, лимит N кандидатов), затем опциональная LLM-проверка «связать ли». Запускается только на создание, кандидаты ограничены → стоимость под контролем. Полноценные эмбеддинги/RAG — вне MVP (подключаются модулем при росте объёма).

#### 4.5 Планировщик — FR-31, FR-32
- APScheduler-задача считывает `settings`; если `morning_report_enabled` — в `morning_report_time` (в `timezone` пользователя) формирует план/аналитику и отправляет в TG.
- По умолчанию выключено (FR-30).

#### 4.6 Веб: API и фронтенд — FR-25…FR-29, FR-33, FR-34
- **REST API (FastAPI):** CRUD `items` (по типам), `tags`, `links`, membership, `comments`, `attachments`, `settings`; auth (`/login`, `/logout`); `/dashboard` (агрегаты + инсайты). Все, кроме `/login`, — за авторизацией.
- **Фронтенд (React SPA):** списки (актуальные/завершённые), редактор записи (все поля, комментарии, связи, вложения), вид проекта (состав), настройки бота, дашборд с инсайтами (Recharts). Без чат-интерфейса (чат — только в TG).
- **Синхронизация (FR-29):** общая БД — единый источник; веб и бот читают/пишут её же. (Real-time push в MVP не обязателен: обновление по опросу/refresh; при желании — SSE/WebSocket позже.)

#### 4.7 Слой ИИ и контроль стоимости — NFR-1, NFR-2
- Абстракции: `LLMClient`, `STTClient`, `OCRClient` (интерфейсы + реализации). Выбор реализации и параметры — из `.env`/конфига.
- **LLM:** `openai` SDK, `base_url`+`model`+`api_key` из конфига. Реализации: YandexGPT (AI Studio, OpenAI-совместимый), DeepSeek, Ollama (локально).
- **STT:** реализация по умолчанию — Yandex SpeechKit (RU, рубли); альтернативы — Whisper (API) / faster-whisper (локально).
- **OCR:** по умолчанию — Yandex Vision OCR (RU); альтернатива — Tesseract (локально).
- **Экономия токенов:** стабильный системный промпт (для cache-hit), минимальный контекст (только релевантные строки, не весь массив), дешёвая модель для парсинга, структурированный JSON-вывод, отсутствие полносканирующих запросов. Ожидаемая стоимость при личном профиле — существенно ниже 1000 ₽/мес.

#### 4.8 Бэкапы и изоляция от ИИ — NFR-4
- Отдельный сервис/cron **`backup`** запускается под **другим OS-пользователем** и монтирует каталог бэкапов, к которому у контейнеров `bot`/`web` **нет прав на запись/удаление** (или бэкап-каталог им вовсе не смонтирован).
- Суточный срез БД (копия SQLite-файла, напр. состояние на конец предыдущего дня), retention N дней.
- Итог: ИИ/бот физически не может изменить или удалить бэкап — контур автономных действий изолирован от резервной копии.

#### 4.9 Безопасность и обратимость — NFR-3, NFR-5, FR-34
- Пароль — argon2; сессия — HTTP-only secure cookie; HTTPS через nginx.
- **TG-доступ:** бот принимает команды только от разрешённого `owner_telegram_id` (allowlist из конфига) — это защита канала TG (FR-34 для бота).
- Обратимость: soft-delete + `audit_log` действий (особенно `actor='ai'`), чтобы автономность ИИ не приводила к необратимой потере.
- Приватность (NFR-3): в конфиге — флаг/список того, что не отправлять во внешний ИИ (уточняется при внедрении; при чувствительных данных — путь Ollama локально).

### 5. Развёртывание

**docker-compose** сервисы: `nginx`, `web`, `bot`, `backup` (+ том с SQLite-файлом, общий для `web`/`bot` на чтение-запись; для `backup` — доступ к копированию, к каталогу бэкапов у `web`/`bot` прав нет).

Конфигурация — через `.env`: токен TG-бота, `owner_telegram_id`, LLM (`base_url`/`model`/`api_key`), STT/OCR-провайдеры и ключи, домен, параметры бэкапа, учётка веб-пользователя (первичная инициализация).

TLS — certbot/Let's Encrypt на домене VPS. nginx: статика SPA + прокси `/api` → `web`.

### 7. Открытые вопросы к реализации (решить до/в начале разработки)

1. **Провайдер ИИ для старта:** YandexGPT (рубли, RU, мультимодальная экосистема) или DeepSeek (дешевле, но оплата из РФ). От этого зависят STT/OCR по умолчанию.
2. **Фронтенд:** подтверждаем React SPA, или предпочитаешь более лёгкий вариант (server-rendered + htmx) ради простоты деплоя?
3. **БД:** SQLite на старте (рекомендация) — ок? Переезд на Postgres тривиален через SQLAlchemy при необходимости.
4. **Связывание (M5):** на старте — эвристика по ключевым словам (дёшево) или сразу лёгкие эмбеддинги? Рекомендация — эвристика, эмбеддинги позже.
5. **Точные промпты** (классификация намерения, извлечение, форматирование плана/аналитики) — финализируются в M2/M4.

---

### 8. Приёмка

Соответствие критериям **AC-1…AC-8** из БТ проверяется поэтапно (см. столбец «Готово, когда» в §6). Итоговая приёмка — прохождение всех AC на развёрнутой на VPS системе.
